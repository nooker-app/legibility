# DOM 가상 렌더링으로 "시각적으로 가장 큰 요소"를 찾아 추출 가중치를 둘 수 있는가

## 결정

**`legibility-core`에는 레이아웃 엔진을 넣지 않는다.** 아이디어의 방향은 맞지만, 코퍼스에서 실측한
손실의 구성이 그것을 **세 번째 우선순위**로 만든다. 대신 (1) 레이아웃 없이 얻을 수 있는 시각 대리
신호 네 개를 채택하고, (2) 아이디어의 **천장**을 헤드리스 Chrome으로 먼저 측정한다(PROBE-C).

이 결정은 아이디어가 틀렸다는 판정이 아니다. **레이아웃이 도울 수 있는 페이지가 130장 중 3장인데,
레이아웃이 전혀 관계없는 이유로 0.000을 받는 페이지가 8장**이라는 측정에 따른 순서 결정이다.

## 왜 이 질문이 나왔는가

Readability는 문자 수를 세고 콤마를 센다. 사람은 그러지 않는다 — 페이지를 열면 본문이 **크게 보여서**
본문인 것을 안다. 그러니 렌더 후 크기를 재서 그쪽으로 가중치를 주면 문자 수보다 현대적이고 정확한
신호가 되지 않겠는가. 이 직관은 옳다. 문제는 "렌더 후 크기"를 얻는 비용과, 그것이 실제로 닫는 손실의
크기다.

## 측정 — 우리가 지금 무엇을 잃고 있는가

mozilla 코퍼스 130장, `crates/legibility-cli/tests/selection-baseline.tsv` 기준(2026-08-06,
커밋 `4ede33c`).

| 구간 | 페이지 수 |
|---|---|
| F1 ≥ 0.95 | 79 |
| 0.80 – 0.95 | 25 |
| 0.40 – 0.80 | 10 |
| < 0.40 | 16 |

**0.000을 받는 16장 중 10장은 잘못 고른 것이 아니라 아무것도 고르지 않았다**(`article: None`).
`lgb explain`은 열 장 전부에서 `candidates 0`을 보고한다 — 후보가 0개다. 이유를 소스에서 확인했다:

| 페이지 | `<body>` 안의 컨테이너 요소 수 | 크기 |
|---|---|---|
| `005-unescape-html-entities` | **0** | 221 B |
| `js-link-replacement` | **0** | 209 B |
| `reordering-paragraphs` | **0** | 2.1 KB |
| `svg-parsing` | **0** | 2.8 KB |
| `hidden-nodes` | **0** | 3.4 KB |
| `missing-paragraphs` | **0** | 3.7 KB |
| `data-url-image` | **0** | 65 KB |
| `mathjax` | **0** | 202 KB |
| `ietf-1` | 3 | 65 KB |
| `bug-1255978` | 387 | 336 KB |

**여덟 장은 `<div>`·`<article>`·`<main>`·`<section>`이 하나도 없다.** `<p>`가 `<body>` 직속 자식이고,
따라서 **본문이 `<body>` 자신**이다. 크기가 없는 것이 아니라 **비교할 상대가 없다.** 페이지가 202 KB든
221 B든 마찬가지다 — 레이아웃 엔진은 여기서 할 말이 없다. 이건 계획서 M4가 이미 명시한
"**body 두 상태 분리** — purity가 floor를 margin 이상 초과하고 어떤 proper subtree도 이기지 못하면
`kind=Article` + `region_is_body_by_argmax`(정당한 승자)"가 아직 구현되지 않은 것이다.

나머지, 실제로 **영역을 잘못 고른** 페이지는 방향으로 갈라진다. 우리 `article.text` 길이를
`expected.html`의 텍스트 길이와 비교한 값:

| 페이지 | F1 | 우리 / expected | 판정 |
|---|---|---|---|
| `dev418` | 0.038 | 0.02× | 너무 좁게 |
| `wikipedia-3` | 0.113 | 0.06× | 너무 좁게 |
| `ehow-1` | 0.364 | 0.22× | 너무 좁게 |
| `simplyfound-1` | 0.408 | 0.28× | 너무 좁게 |
| `table-style-attributes` | 0.434 | 0.28× | 너무 좁게 |
| `hukumusume` | 0.541 | 0.48× | 너무 좁게 |
| `wordpress` | 0.263 | 0.51× | 너무 좁게 |
| `quanta-1` | 0.708 | 0.55× | 너무 좁게 |
| `pixnet` | 0.348 | 3.31× | 너무 넓게 |
| `nytimes-5` | 0.501 | 3.02× | 너무 넓게 |

**여덟 장은 너무 좁고 세 장은 너무 넓다.** 너무 좁은 쪽은 본문이 형제들로 쪼개져 있고 우리가 그중
하나만 집은 것이다 — 해법은 순위 재조정이 아니라 계획서 M6의 "region growth with bounded skip"이고,
레이아웃은 여기서 부수적이다(어느 형제가 큰지가 아니라 **여러 형제를 이어붙일지**가 문제다).
너무 넓은 세 장이 시각 크기 신호가 실제로 겨냥하는 유일한 모집단이다: 본문 + 주변 가구를 함께 쥔
조상을 골랐고, 렌더 크기를 알면 본문 칼럼만 남길 수 있다.

**요약: 물질적으로 손실이 나는 21장 중 레이아웃이 확실히 돕는 것은 3장, 부분적으로 돕는 것은 8장,
전혀 돕지 못하는 것은 10장이고 그 10장이 가장 큰 단일 블록이다.**

## 왜 코어에 넣지 않는가 — 네 개의 확정된 계약과 충돌한다

크기를 알려면 레이아웃이 필요하고, 레이아웃은 (1) CSS 캐스케이드 전체, (2) 박스 생성 + flow/flex/grid,
(3) 폰트 메트릭과 셰이핑, (4) 뷰포트를 요구한다. 각각이 이미 커밋된 계약에 걸린다.

1. **네트워크·파일시스템 없음** (M3 exit gate, CI가 `SystemTime|Instant::now|std::fs|std::net`을 grep으로
   거부). 외부 스타일시트는 `<link href>`이고 코어는 그것을 가져올 수 없다. §1.10.2가 이미
   "v1은 외부 CSS를 파싱하지 않는다"를 한계로 기록해 두었다. 인라인 `style`과 `<style>` 블록만으로 하는
   레이아웃은 레이아웃이 아니라 **확신을 가진 틀린 레이아웃**이고, 그건 레이아웃이 없는 것보다 나쁘다 —
   그 결과가 region 선택을 **주도하게** 되기 때문이다.
2. **S3: native / wasm32-wasip1 / headless Chrome에서 바이트 동일 출력.** 레이아웃에서 어려운 부분은
   텍스트 측정이고, 텍스트 폭은 실제 폰트에 달려 있다. 폰트 가용성은 호스트마다 다르다 — 폴백 체인이
   존재하는 이유가 그것이다. 폰트가 다르면 줄 수가 다르고, 줄 수가 다르면 높이가 다르고, "가장 큰 요소"가
   달라진다. S3를 지키려면 호스트에 절대 묻지 않고 **자체 메트릭 테이블을 동봉**해야 한다. CJK 폰트
   하나가 메가바이트 단위이고, 이 프로젝트는 MV3와 iOS 임베딩이 목표다.
3. **§1.2 numeric policy**가 transcendental 함수를 금지하고 모든 나눗셈을 `guarded_div`로 묶는다.
   레이아웃은 부동소수 연산 덩어리다. D2가 Q16.16을 사전 승인된 escape hatch로 두었으니 불가능하지는
   않지만, 표면이 크다.
4. **결함 ④가 속도다.** PROBE-A(ADR 0002)가 예산의 근거를 127.9 MiB/s로 고정했다. CSS 셀렉터 매칭이
   레이아웃에서 가장 비싼 부분이고, 이 프로젝트가 class/id를 빌드 타임 Aho-Corasick으로 처리하는 이유가
   바로 그 비용이다. 레이아웃 패스는 낙관적으로도 파싱과 같은 자릿수이고 현실적으로 2–5배다.

## 대신 채택하는 것 — 레이아웃 없는 시각 대리 신호

사용자의 통찰을 **메커니즘에서 분리**하면, "시각적으로 크다"는 서로 다른 주장 몇 개의 합이다.

| 시각적 사실 | 레이아웃 없이 얻는 방법 | 지금 상태 |
|---|---|---|
| 수직 방향으로 길다 | 텍스트 길이 | **이미 있음** — `prose_len` |
| 본문 칼럼이 넓다 | 조상 사슬·깊이 | 부분적으로 anchor strength |
| 접힌 선 위에 있다 | **문서 순서** — `flatten()` 이후 `NodeId`가 곧 문서 순서다 | **공짜인데 안 쓰고 있음** |
| 역할 대비 폰트가 크다 | 인라인 `style` 스캔 (`a11y.rs`가 이미 `font-size:0`을 본다) | 스캔은 있고 버킷은 없음 |
| 미디어가 자리를 많이 차지한다 | `<img>`/`<video>`의 `width`·`height` **속성** — 마크업에 그냥 있다 | **전혀 안 쓰고 있음.** `width`는 이미 interned(`AttrName` 22, HN indentation용)이고 `height`는 아니다 |

마지막 항목이 가장 저렴하고 가장 새롭다. 현재 이미지는 region 점수에 **아무 기여도 하지 않는다**.
히어로 이미지와 캡션을 가진 본문이 이미지 없는 사이드바에 통계로 지는 형태가 원리적으로 가능하다.
`width`·`height` 속성은 레이아웃 없이도 "이건 시각적으로 크다"를 직접 말해 준다.

이 네 개는 사실상 무료이고, 사용자가 원한 신호의 대부분을 레이아웃 엔진 없이 준다.

## 근사할 수 없는 것 — 정직하게

문서 순서가 **거짓말을 하는** 경우는 대리 신호로 잡을 수 없다: `order:`, `flex-direction: row-reverse`,
`grid-template-areas`가 시각 순서를 문서 순서와 다르게 만드는 페이지, 그리고 사이드바의 텍스트가 본문보다
많은 다단 매거진 레이아웃. 실재하는 형태다. 다만 **빈도에 대한 측정이 우리에게 없고**, 위 표에서 그
후보는 130장 중 3장이다.

## PROBE-C — 천장을 먼저 재고, 그다음에 만들 것을 정한다

계획서 M2는 S3의 세 번째 determinism leg으로 **헤드리스 Chrome**을 이미 요구한다(현재 미구현:
`.github/workflows/`가 없고 chrome runner도 없다). 그것이 생기는 순간 **진짜 레이아웃 엔진이 CI 안에
들어와 있다.** 그러면 아이디어의 천장은 엔진이 아니라 스크립트 한 장으로 측정할 수 있다.

> 코퍼스 각 페이지를 헤드리스 Chrome에서 열고 모든 요소에 대해 `getBoundingClientRect()` +
> `getComputedStyle`을 수집한다. "렌더된 텍스트 면적이 가장 큰 요소"를 계산하고, 그것을
> `expected.html`에 대해 **같은 token-F1으로 채점**한다. 이것이 아이디어의 **천장**이다.

결과가 어느 쪽으로 나와도 결론이 난다.

- 우리가 지는 페이지에서 시각 오라클이 우리를 **이긴다** → 아이디어가 증명되었고, 그다음에 근사 방법을
  논쟁하면 된다. 근사 대상이 무엇인지도 이 측정이 알려준다.
- **비긴다** → 신호가 이미 `prose_len` 안에 들어 있다는 뜻이다. 숫자와 함께 닫는다.
- 오라클 **자신이 자주 틀린다**(sticky header, 전면 광고, 무한 스크롤 컨테이너) → 천장이 낮다.
  이것도 숫자와 함께 닫는 결론이다.

`m0-gate.sh`가 이미 native == wasip1 바이트 동일성을 확인한다. Chrome leg은 그 옆자리다.

## 같은 스크립트의 두 번째 소득 — 이쪽이 더 클 수 있다

§1.10.2가 "외부 CSS로만 숨겨진 노드를 놓친다"를 **명명된 한계**로 기록하고, 놓치는 케이스를 코퍼스에
남겨 두라고 요구한다. Chrome은 외부 CSS가 무엇을 숨기는지 공짜로 안다.

그 출력 — 외부 스타일시트에 의해 숨겨진 노드 목록 — 은 **우리가 파생시킨 산출물**이므로 D9에 걸리지
않고 커밋할 수 있다. 코퍼스 메타데이터로 두면, **코어가 CSS를 단 한 줄도 파싱하지 않으면서** a11y
필터를 실제 가시성에 대해 채점할 수 있다. 시각 크기 신호보다 이쪽이 더 값어치가 있을 가능성이 높다 —
전자는 3장을 겨냥하고 후자는 계획서가 스스로 인정한 구멍을 닫는다.

## 순서

1. **M4의 `<body>` argmax 케이스.** 0.000짜리 8장, 단일 최대 블록, 이미 명세돼 있음.
2. **M6의 region growth with bounded skip.** 너무 좁게 고른 8장.
3. **무료 시각 대리 신호 네 개** — 특히 `<img>`/`<video>`의 `width`·`height`(`height` interning 필요).
4. **PROBE-C** — M2의 Chrome leg이 생긴 뒤. 만들기 전에 천장을 잰다.
5. **코어 레이아웃 엔진** — 하지 않는다. 외부 CSS 한계·S3·크기 예산을 동시에 깨고, 측정된 천장이
   130장 중 3장이다.

## 반증 조건

PROBE-C에서 시각 오라클이 **우리가 0.80 미만인 21장 중 12장 이상**을 0.95 이상으로 올리면 위 순서는
틀린 것이고 이 ADR을 폐기한다. 위 표는 그 반대를 예측한다 — 그 21장 중 10장은 후보가 0개이고, 오라클도
`<body>`밖에 고를 것이 없다.
